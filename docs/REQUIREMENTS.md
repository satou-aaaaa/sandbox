## 1. プロジェクト概要

### 1.1 背景

発注者は行政書士を副業として開業予定であり、限られた稼働時間（平日夜間・週末）で
継続的に案件対応できる体制を作るため、建設業許可の新規申請・更新業務を
できる限りソフトウェアで自動化する方針を採っている。国土交通省が建設業許可の
電子申請システム（JCIP）の外部インターフェイス仕様を公開しており、かつ
建設業許可は「5年ごとの更新」「毎年の決算変更届」という反復業務を持つため、
自動化の効果が出やすい分野として選定した。

### 1.2 目的

建設業許可の新規申請業務について、次の3工程をソフトウェアで支援する。

1. **要件判定** — 申請者情報から、建設業許可の法定5要件を満たすかを機械的にチェックする
2. **書類生成** — 判定を通過した申請者について、申請書類の下書きを自動生成する
3. **更新リマインド** — 許可取得後、5年後の更新期限・毎年の決算変更届期限を自動計算し通知する

行政書士本人が行うのは「最終内容の確認・押印・提出」のみに絞り込むことを目指す。

### 1.3 重要な制約（法的前提）

- 行政書士は登録制の独占業務であり、2026年の法改正により
  「報酬を得て官公署に提出する書類を作成すること」が明確に独占業務と規定され、
  無登録での実施には刑事罰が科される。
- 本システムがどれだけ自動化されても、**最終書類の内容確認と提出代理は
  登録行政書士本人が行う**ことが必須であり、これを省略・代替する機能を
  実装してはならない（詳細は `docs/DESIGN.md` の設計原則を参照）。
- 本システムの判定結果は「申請前の一次スクリーニング」であり、
  「許可が下りることを保証するもの」ではない。UIやドキュメント上の文言でも
  この前提を誤解させる表現をしないこと。

## 2. 用語集

| 用語 | 説明 |
|---|---|
| 経営業務管理体制 | 建設業許可の法定要件の一つ。経営業務の管理を適正に行う体制があること |
| 専任技術者 | 営業所ごとに配置が必要な、一定の資格・実務経験を持つ技術者 |
| 財産的基礎 | 建設業許可の法定要件の一つ。一定の自己資本・資金調達能力等があること |
| 欠格要件 | 該当すると許可を受けられない事由（破産、許可取消歴、刑罰歴など）のネガティブリスト |
| 誠実性 | 請負契約に関して不正・不誠実な行為をするおそれが明らかでないこと |
| 一般建設業／特定建設業 | 許可区分。下請契約の金額規模等により区分され、特定建設業は要件がより厳格 |
| 様式第一号等 | 建設業許可申請で使用する国交省・都道府県指定の帳票番号 |
| JCIP | 建設業許可・経営事項審査電子申請システム（国交省が運営する電子申請基盤） |
| 決算変更届 | 毎事業年度終了後に提出が必要な、事業年度終了届を含む一連の届出の通称 |
| 一次スクリーニング | 本システムによる判定は最終判断ではなく予備的なチェックに過ぎないことを示す言葉 |

## 3. 想定利用者・利用シーン

- **主利用者**: 発注者本人（行政書士登録後、自身の業務で使用する）
- **想定シーン**: 顧客（建設業許可を取得したい事業者）から必要情報をヒアリングし、
  その情報を本システムに入力 → 要件判定結果を確認 → 書類下書きを生成 →
  発注者本人が内容を確認・修正 → 正式様式へ転記し提出、という一連の流れの中で
  ①要件判定と②書類下書き生成を担う。
- 本フェーズ（M2）では、顧客が直接システムを操作するフォームは対象外とし、
  発注者本人がデータを入力・実行するCLI/スクリプト操作を前提とする
  （M3以降、発注者本人が操作するローカルWebフォームを追加しているが、
  顧客が直接入力する想定は変わらず対象外のまま。FR-4.2参照）。

### 4.6 入力内容の整合性チェック（M7）

競合調査の結果、AI等を用いた「記載ミス・添付漏れの自動チェック」が
差別化要因として挙げられていた。本ツールはNFR-4（外部送信禁止）により
顧客データを外部AI APIへ送信できないため、同等の価値をルールベースの
静的チェックで実現する。既存の要件判定（§4.1、法定要件の合否判定）とは
明確に分離し、**合否判定には一切影響しない「気づき」情報**として提供する。

| ID | 内容 | 状態 |
|---|---|---|
| FR-6.1 | 代表者氏名と経営業務管理責任者（証明を受ける者）の氏名が異なる場合、裏付け書類の確認を促す注記を出せること | 実装済み（`src/eligibility/consistencyChecks.js` の `checkConsistency`） |
| FR-6.2 | 実務経験年数等の数値項目が負の値、または明らかに非現実的な大きさ（入力ミスの疑い）である場合に注記を出せること。しきい値は「負の値、または80年超」とする（`MAX_PLAUSIBLE_YEARS = 80`。法的根拠のある値ではなく、実務キャリアとして現実的にありえない大きさという簡易基準） | 実装済み |
| FR-6.3 | 同一人物が複数営業所の専任技術者として重複登録されている場合に、専任性（原則1営業所専任）に関する注記を出せること | 実装済み |
| FR-6.4 | 上記の注記は要件判定エンジンの `eligible` の算出結果に影響を与えないこと（既存の判定ロジック・既存テストへの後方互換性を保つ） | 実装済み（`consistencyWarnings` は `EligibilityResult` への追加フィールドのみで、`eligible`/`checks`/`blockingIssues` の算出処理は変更していない。`test/consistencyChecks.test.js`・`test/eligibility.test.js` で検証） |

### 4.7 経営事項審査（経審）書類準備支援（M8）

競合調査で経審関連書類（財務諸表・工事経歴書）の生成が差別化要因として
挙げられたことを踏まえた機能。ただし調査の結果、経審の点数計算
（X1・X2・Y・Z・W・総合評定値Ｐ）は国が定期改定する換算表を用いる
専門領域であり、かつY点は法令上民間の登録機関が算出するものであるため、
本ツールでの自動計算は行わない（ADR-0009）。工事経歴書は決算変更届
（既存M4のリマインド対象）でも毎事業年度必要になる書類であり、点数計算を
一切伴わない書類サマリー生成として着手する。

| ID | 内容 | 状態 |
|---|---|---|
| FR-7.1 | 経審の評点（X1・X2・Y・Z・W・総合評定値P）の自動計算は行わないこと（ADR-0009） | 方針決定（対象外と明記） |
| FR-7.2 | 経営規模等評価申請書・経営状況分析申請書そのものの生成は本フェーズでは対象外とすること | 方針決定（M9以降で検討） |
| FR-7.3 | 財務諸表（様式第十五号〜十七号）のサマリー生成は本フェーズでは対象外とすること（データ項目数が多く別途調査が必要なため） | 方針決定（M9以降で検討） |

## 6. スコープ外（本フェーズで対応しないこと）

- JCIP電子申請システムとの自動連携（データ送信の自動化）
- 複数都道府県への対応（様式・運用差異の吸収）
- 顧客向け入力フォーム・ポータルサイトの構築
- 更新リマインドの自動送信（メール等の通知連携）
- 正式様式（国交省・都道府県指定の罫線レイアウト）に完全準拠したPDF出力
  （本フェーズは内容確認用のサマリー出力のみ）
- 外部AI API（ChatGPT等）へ申請者データを送信して記載内容をチェックする機能
  （NFR-4により対象外。同等の価値はルールベースの整合性チェック（§4.6）で実現する）
- 経営事項審査（経審）の評点計算（X1・X2・Y・Z・W・総合評定値P）、
  経営規模等評価申請書・経営状況分析申請書そのものの生成、財務諸表
  （様式第十五号〜十七号）のサマリー生成（M7の競合調査で識別したが、
  国が定期改定する換算表・法令上民間機関が算出するY点を扱う専門領域で
  あるため対象外とした。§4.7・ADR-0009参照。工事経歴書＜様式第二号＞の
  サマリー生成のみM8として対応する）
