# 要件定義書 — 在留資格「技術・人文知識・国際業務」申請支援モジュール

version: 0.1 / 2026-09 作成
対象: kensetsu-kyoka-toolkit の拡張（許認可自動化コアの5例目としての実装、事業提案の柱（C）の第一弾）

## 0. 本書の位置づけ

本書は、事業提案の柱（C）「外国人材関連（中長期）」の第一弾として、
在留資格「技術・人文知識・国際業務」（通称: 技人国ビザ）のうち、
**在留資格認定証明書交付申請（新規に海外から招へいするケース）のみ**を
対象とした要件定義書である。コアの設計は`docs/DESIGN_kobutsu-core.md`を
参照。開発環境構築・コーディング規約・Git運用は既存の
`docs/DEVELOPMENT_GUIDE.md`を適用する。

**本モジュールは他の3モジュール（産廃・民泊・下請けポータル）よりも
専門性・リスクが高い分野を扱う。1.3節・6章を特に注意して読むこと。**

## 1. プロジェクト概要

### 1.1 背景

出入国在留管理行政（入管業務）は、行政書士の業務範囲の中でも需要が
大きい分野であり、事業提案でも柱（C）として中長期構想に位置づけて
いた。数ある在留資格の中でも「技術・人文知識・国際業務」は、外国人
材の就労系在留資格として最も件数が多く、かつ判定基準が「学歴」
「職務内容との関連性」「報酬額」という比較的定型化しやすい3要素に
整理できるため、書類自動化との相性が良いと判断し、第一弾として選定した
（技能実習・特定技能は監理団体・登録支援機関を介する複雑な制度、
経営管理ビザは事業計画・出資額等さらに専門的な要件があり、いずれも
本フェーズでは対象外とする）。

在留資格には3月・1年・3年・5年の4種類の在留期間があり、更新が必要
という点は建設業許可・産廃許可の「有効期限型」リマインドと構造的に
近いが、**許可時に期間が可変で、かつ更新のたびに期間が変わりうる**
（初回1年、更新時に3年になる等）点が、固定5年更新の建設業許可・
産廃許可とは異なる。

### 1.2 目的

1. 学歴・職務内容の関連性・報酬基準の該当性を判定する
2. 在留資格認定証明書交付申請書のサマリーをdocxで生成する
3. 在留期間の満了リマインドを、可変の期間に対応した形でコアの
   リマインドエンジンに登録する

### 1.3 重要な制約（他モジュールより厳格。必読）

- **申請取次行政書士としての届出が別途必要**: 行政書士が出入国在留
  管理局へ外国人本人に代わって書類を提出する（申請取次）には、
  行政書士登録に加えて、地方出入国在留管理局長への届出・研修受講が
  必要となる。単に行政書士登録が完了しただけでは、他の許可種別と
  異なり「代理人として作成した書類を本人が窓口へ持参する」形にしか
  ならず、取次までは行えない。この届出状況を発注者が満たしているかを
  必ず事前に確認すること
- 出入国管理及び難民認定法・関連省令・運用基準は他の許認可分野よりも
  改定頻度が高いとされる。本ツールの判定ロジックは「申請前の一次
  スクリーニング」であることを、他モジュール以上に強調して明示する
  こと。誤った判定は外国人本人の在留資格・雇用に直接影響するため、
  特に慎重な文言設計が必要
- 本システムがどれだけ自動化されても、最終的な書類内容の確認・
  提出（取次）は登録行政書士（申請取次の届出を満たす者）本人が
  行うことが必須であり、これを省略・代替する機能は実装しない
  （既存原則の継承だが、本モジュールでは特に重要）
- 外国人本人の個人情報（旅券情報・学歴・職歴等）を扱うため、
  NFR-4（外部送信禁止）を特に厳格に遵守すること

## 2. 用語集

| 用語 | 説明 |
|---|---|
| 技術・人文知識・国際業務（技人国） | 理学・工学等の自然科学、法律学・経済学等の人文科学の知識を要する業務に従事するための在留資格 |
| 在留資格認定証明書交付申請 | 海外から外国人を新規に招へいする際、上陸審査を円滑にするために事前に申請する手続（受入企業側が代理提出することが多い） |
| 申請取次 | 行政書士等が、本人に代わって出入国在留管理局の窓口へ出頭・提出する行為。別途届出・研修が必要 |
| 所属機関カテゴリー | 受入企業を、提出書類の簡素化のために規模・実績等で区分したもの（カテゴリー1〜4） |
| 学歴と職務内容の関連性 | 大学等での専攻科目と、従事する業務内容が関連していることを示す要件 |

## 3. 想定利用者・利用シーン

既存モジュールと同じ利用形態（発注者本人が行政書士登録・申請取次の
届出完了後、CLI/スクリプト操作で使用）。想定シーンとして、企業
（受入機関）から外国人材の採用に伴う就労ビザ手続きの依頼を受け、
①学歴・職務内容・報酬の要件判定→②申請書サマリーの生成→
③在留期間満了のリマインド設定、という流れを想定する。

## 4. 機能要件

### 4.1 技人国ビザ 要件判定エンジン

| ID | 内容 | 備考 |
|---|---|---|
| FR-G1.1 | 学歴要件（自然科学・人文科学分野の技術・知識を要する業務の場合: 当該技術/知識に関連する科目を専攻して大学卒業相当以上、または専修学校専門課程修了相当）を判定できること | 根拠: 入管法基準省令（e-Gov法令検索で原文確認済み・2026年9月）別表第一の二の表・技術・人文知識・国際業務の項 |
| FR-G1.2 | 学歴で要件を満たさない場合、実務経験による代替要件を判定できること。基準は業務区分により異なり、①自然科学・人文科学分野の技術・知識を要する業務は**10年以上**の実務経験、②外国の文化に基盤を有する思考・感受性を必要とする業務（通訳・翻訳・語学指導等の「国際業務」区分）は**3年以上**の実務経験（ただし大学卒業者が翻訳・通訳・語学の指導に従事する場合はこの3年要件自体が不要） | **一次資料（入管法基準省令）で確認済み**。当初案の「3年」という数字は国際業務区分としては正しかったが、①区分の10年という基準・②区分の大学卒業者向け3年要件免除は当初案になかった。なお、①区分には情報処理技術に関する法務大臣告示指定の試験合格・資格保有者は学歴・実務経験要件自体が免除される例外があるが、対象となる試験・資格の一覧は法務大臣告示（e-Gov法令検索の対象外）に定められており本フェーズでは未検証のため対象外とする（4.5節） |
| FR-G1.3 | 専攻科目（またはこれに相当する実務経験の内容）と、従事する職務内容との関連性について、機械的な自動判定ではなく、判定材料となる入力（専攻分野・職務内容の自由記述）を整理し、必ず人手確認を促す警告を出せること | 関連性の判断は個別の審査官裁量が大きく機械判定が困難なため、建設業許可の`seijitsusei.js`と同様、自己申告＋警告に留める |
| FR-G1.4 | 報酬基準（日本人が同等の業務に従事する場合と同等額以上）について、比較対象となる給与水準の入力（自社の日本人従業員の同種業務の給与等）を受け取り、下回っていないかを判定できること | |
| FR-G1.5 | 上記をまとめて総合判定し、未充足理由の一覧を人間可読なテキストレポートに整形できること。判定結果には「これは一次スクリーニングであり、最終的な該当性は出入国在留管理局が個別に審査する」旨を他モジュール以上に強調した文言を必ず含めること | 1.3節の制約を出力文言レベルで担保する |

### 4.2 技人国ビザ 書類生成

| ID | 内容 | 備考 |
|---|---|---|
| FR-G2.1 | 在留資格認定証明書交付申請書の記載内容サマリーをdocxで生成できること | |
| FR-G2.2 | 所属機関（受入企業）カテゴリーに応じて必要となる添付書類の一覧をチェックリストとして出力できること（民泊モジュールの必要書類チェックリストと同じ考え方） | カテゴリー1〜4ごとに必要書類が異なる点を反映する。**カテゴリーの判定基準自体は、他の要件（欠格事由・報酬基準等）と異なり法令・省令ではなく出入国在留管理庁の運用要領（行政上の取扱い）に基づくものであり、一次資料（法令）による検証はできない**。そのため本フェーズではカテゴリー自体の自動判定は行わず、利用者が別途確認して入力する`companyCategory`（手入力）を前提とする（設計は当初案どおり） |
| FR-G2.3 | 各様式はコアの共通ヘルパーを再利用し、「正式提出様式ではない」旨、および「最終的な該当性は個別審査による」旨の両方を明記すること | |

### 4.3 在留期間満了リマインド（コアへの登録）

| ID | 内容 | 備考 |
|---|---|---|
| FR-G3.1 | 在留期間（3月・1年・3年・5年のいずれか）を入力として受け取り、在留カードに記載された在留期限を基準に更新（在留期間更新許可申請）のリマインドを算出できること | 建設業許可・産廃許可の`calcRenewalSchedule`は「5年固定」を前提にしているため、そのまま流用できない。期間を可変で受け取れる新しい計算関数が必要（設計書で詳細化） |
| FR-G3.2 | 更新申請は在留期限の3ヶ月前から可能であり、期限までに申請すれば、審査中の期間も引き続き在留できる「特例期間」があることを踏まえ、余裕を持ったリマインドタイミング（例: 満了90日前・60日前・30日前）を算出できること | **特例期間は「処分がされる時、又は在留期間満了日から2ヶ月が経過する日が終了する時」のいずれか早い時までと確認済み（出入国在留管理庁公式サイトで確認・2026年9月）。**リマインド計算自体（満了90/60/30日前）はこの特例期間の長さに直接依存しないため設計への影響はないが、出力文言に「特例期間は2ヶ月であり、無期限に在留できるわけではない」旨を明記し、誤解を防ぐこと |

### 4.4 インテイク

既存と同様、CLI/スクリプト操作を前提とする。

### 4.5 スコープ外（本フェーズで対応しないこと）

- 在留資格「技術・人文知識・国際業務」以外の在留資格（技能実習・
  特定技能・経営管理・家族滞在 等）
- 在留資格変更許可申請（すでに日本国内にいる外国人の資格変更）:
  ✅ 2026年9月実装済み（`documents/henkoShinseisho.js`。入管法20条。
  8章参照）。当初は新規招へい（認定証明書交付申請）のみ対象としていたが、
  在留資格自体の該当要件は申請経路によらず同一であることを確認し、
  既存の判定ロジックを再利用する形で追加した
- 在留申請オンラインシステムへの電子申請の自動化
- 高度専門職ポイント計算
- 永住許可・帰化許可申請

### 4.6 非機能要件

既存NFR-1〜7・NFR-C1〜C3を継承する。加えて:

| ID | 内容 |
|---|---|
| NFR-G1 | 外国人本人の旅券番号等の識別情報は、必要最小限の保持に留め、書類生成に使わない情報は入力データモデルに含めないこと |
| NFR-G2 | 判定結果・生成書類のすべての出力に、「一次スクリーニングであり出入国在留管理局の個別審査に拠る」旨の文言を含めること（FR-G1.5・FR-G2.3） |

## 5. 受け入れ基準

1. `npm test` が既存分＋新規追加分すべて成功すること
2. 既存モジュールの出力・挙動が変化しないこと（回帰テスト）
3. ダミーデータから学歴・報酬要件の判定、および2種類の出力
   （申請書サマリー・添付書類チェックリスト）が生成できること
4. 在留期間（3月/1年/3年/5年）を変えて満了リマインドを計算した際、
   それぞれ正しい満了日・リマインド日が算出されること

## 6. 前提条件・依存事項（特に重要）

- **発注者が申請取次の届出・研修を完了していること**（1.3節）。
  未完了の場合、本モジュールの「取次」を前提とした運用はできない
  （書類作成支援のみに用途を限定するか、届出完了を待つ必要がある）
- 出入国在留管理庁の公表資料（「技術・人文知識・国際業務」の上陸許可
  基準、所属機関カテゴリーの区分基準、在留期間更新の運用）を一次資料
  として確認し、4章の判定基準を実装前に確定すること
  → **上陸許可基準（学歴・実務経験・報酬）・在留期間の区分（3月/1年/3年/5年）・
  更新申請の特例期間（2ヶ月）は2026年9月に確認済み**（入管法基準省令・
  出入国在留管理庁公式サイト）。FR-G1.1・FR-G1.2・FR-G3.2に反映済み。
  **所属機関カテゴリーの区分基準のみ、法令ではなく行政上の運用要領に
  基づくため一次資料（法令）による検証はできず、本フェーズでは
  カテゴリー自体の自動判定を対象外とした**（FR-G2.2参照）
- 対象様式（在留資格認定証明書交付申請書）の最新版を出入国在留管理庁
  公式サイトから取得すること（様式は改定頻度が高いため、実装直前に
  再確認すること）
