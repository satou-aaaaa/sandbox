# Issue/PR定期対応（kensetsu-kyoka-toolkit）

この kensetsu-kyoka-toolkit（satou-aaaaa/sandbox）リポジトリのオープンな issue・pull request を確認し、対応する。作業を始める前に、まずリポジトリルートの CLAUDE.md を読み、プロジェクトの規約（ビルドレスJS+JSDoc構成、外部送信禁止、判定ロジックへの法令根拠の明記、単一JSONファイル永続化、Git運用方針、テストコマンド）を必ず確認すること。

[README.md](README.md) の「共通のきまり」（節約モード・Claude が要らない作業は CI へ）にも従う。

## Pull Request（Dependabot等、既にオープンなもの）

1. `gh pr list --state open` でオープンなPRを一覧する。それぞれについて:
   - **Dependabotの依存パッケージ更新PR**: patch/minor の更新は `.github/workflows/dependabot-automerge.yml` が自動マージを予約しており、必須チェックが通ればGitHubがマージする。ここで扱うのは、(a) メジャー更新、(b) チェックが失敗して止まっているもの、(c) コンフリクトで止まっているもの だけ。`gh pr checks <N>` でCI状態を確認する。
     - CIが完全に緑で自動マージ予約が無い（メジャー更新など）ものは、下記のメジャー更新の確認をしたうえでマージする（`gh pr merge <N> --squash --delete-branch`）。
     - チェックが失敗している場合は、マージ判断の前に実際の失敗ログを確認する（`gh run view <run-id> --job <job-id> --log`）。
       - 既知の一時的な問題として、`npm audit signatures` ステップが `EMISSINGSIGNATUREKEY` で失敗することがある（npmレジストリ側の証明書伝播遅延によるもので、依存更新自体とは無関係）。これだけが失敗原因なら、失敗したジョブを再実行し（`gh run rerun <run-id> --failed`）、完了を待ってから緑になればマージする。
       - それ以外の失敗は本物の回帰である。マージせず、`gh pr comment <N> --body "..."` で該当するエラーメッセージを引用しながらマージしない理由を説明するコメントを残し、PRはオープンのままにする。
     - **メジャーバージョンアップ**については、CIが緑でもそのツール自体をCIが検証していない場合がある（例: Strykerによるミューテーションテストは `npm run test:mutation` でのみ実行され、CLAUDE.mdのテスト節に明記のとおりCIには含まれない）。CIで検証されないツールのメジャーアップデートをマージする前に、`git worktree add /tmp/pr-check-<N> origin/<ブランチ名>` でPRのブランチを別ディレクトリにチェックアウトし、`npm ci` を実行した上で、影響を受けるツールを小さくスコープを絞って実行し（例: Strykerの更新なら `npx stryker run --mutate "src/succession/heirs/fraction.js"` 等、1ファイルに絞った実行）、正常に動作することを確認してからマージする。確認後は `git worktree remove /tmp/pr-check-<N> --force` で後片付けする。
     - Dependabotの依存更新PRにマージコンフリクトがある場合（`mergeStateStatus: DIRTY`）は、`gh pr comment <N> --body "@dependabot rebase"` とコメントして次回の実行時に再確認する（package.json/package-lock.jsonの手動でのコンフリクト解消はしない）。
   - **issue起点で自分（このルーティンの過去の実行）が作成したPR**: 下記「Issue」節の手順（CIチェック→マージ）に従う。CIが緑でも `mergeable_state` が `dirty`（他のPRの先行マージでmainが進み、コンフリクトが生じた場合を含む）なら、force-pushや履歴の書き換えはせず、下記「コンフリクト解消の手順」に従って解消してから再度CIを待ち、マージする。
     - PR本文に「`agent/` は保護パスのため人手マージ」等の記載があっても、CIが緑でコンフリクトが無ければこのルーティンでマージしてよい（発注者から包括的な承認済み。2026-09-30。この注記は `agent/cycle.mjs` 側の自動運用が人手を必要とする際に残すものであり、本ルーティン（対話セッション経由の定期実行）には別途この承認が及ぶ）。ただし、変更内容が `agent/policy.js` のガードレール（許可リスト・保護パス判定・日次上限・キルスイッチ・レビュー/リバートの判定ロジック）自体を弱める・迂回するように見える場合は、マージせず発注者に確認すること。
   - **Dependabot以外の、他者・想定外の送信元からのPR**（上記の「自分が作成したPR」を除く）: 自動マージしない。本プロジェクトは個人開発であり、発注者以外からのPRは必ず人間によるレビューを要する。内容を読み、要約・懸念点・安全そうかどうかを含む具体的なコメントを残すが、マージするかどうかの判断は発注者に委ねる。

### コンフリクト解消の手順（自分が作成したPRのみに適用。force-push・履歴の書き換えはしない）

1. `git fetch origin main` と `git fetch origin <PRのブランチ>` で最新化する。
2. `git worktree add /tmp/pr-<N> origin/<ブランチ>` で別ディレクトリにチェックアウトし、そこで作業する（現在のセッションの作業ブランチには触れない）。ローカルブランチを作り直す（`git checkout -b <ブランチ名>`）。
3. `git merge origin/main --no-edit` でmainを取り込む。コンフリクトが出たら中身を読んで解消する:
   - 両側が独立した追加（新しいテストケース・ADRへの追記・JSDoc型への新しいフィールド・import文への新しい名前の追加など）であれば、両方を残す（どちらかを消さない）。
   - ADRのAmendment番号など連番が衝突する場合は、後から解消する側を次の空き番号に振り直す。
   - 判定ロジック（合否・reasons・warnings）や `agent/policy.js` のガードレール自体が両側で異なるロジックに変更されている場合は、機械的に結合せず、意図を理解した上で解消する。判断がつかない場合はマージを保留し、PRにその旨をコメントする。
4. 解消後、`npm ci`・`npm test`・`npm run typecheck`・`npm run lint` をこのworktreeで実行し、すべて通ることを確認する（1つでも失敗したら、原因を修正するか、解消をやり直す）。
5. `git add -A && git commit --no-edit` でマージコミットを作り、`git push origin HEAD:<元のブランチ名>` でPRのブランチへpushする（force pushはしない）。
6. `git worktree remove /tmp/pr-<N> --force` で後片付けする。
7. GitHub側のCI（CodeQL・test等）の完了を待ち、すべて緑で `mergeable_state` が `clean` になったらマージする。他のPRが先にマージされて再度コンフリクトが生じた場合は、同じ手順をもう一度行う。

## Issue（確認→PR作成→CIチェック→マージまでを一連で実行）

1. `gh issue list --state open` でオープンなissueを一覧する。
2. まだ対応していない（自分のコメント・自分が作成した紐づくPRがまだ無い）issueについて、内容を精読し分類する。
   - **プロジェクトの既存の規約に合致する、明確でスコープの定まったバグ報告・機能要望**（CLAUDE.md参照: ビルドレスJS+JSDoc、`src/licenses/`配下の許可種別ごとの構造、判定ロジックにはe-Gov法令検索（https://laws.e-gov.go.jp）で確認済みの法令根拠が必要、`test/`配下の既存テストパターンに準拠、等）:
     a. 既存コードの類似箇所を数件読んでパターンを合わせた上で修正・実装する。
     b. `npm test`・`npm run typecheck`・`npm run lint` がすべてローカルで通ることを確認する。
     c. 作業用ブランチを切ってpushし、issue番号を説明文に明記したPRを作成する（`gh pr create`）。
     d. CIの完了を待ち、`gh pr checks <N>` で状態を確認する。CIが完全に緑なら自動マージする（`gh pr merge <N> --squash --delete-branch`）。`mergeable_state` が `dirty` なら、上記「コンフリクト解消の手順」に従って解消してから再度CIを待ち、マージする。issueに完了報告のコメントを残す。
     e. CIが失敗した場合は、上記Dependabot節と同じ基準で一時的な問題（`npm audit signatures`のEMISSINGSIGNATUREKEY等）かどうかを見極め、一時的なら再実行して緑になればマージする。実装自体に起因する本物の失敗であれば、その場で原因を修正して再度a〜dをやり直す（何度か試みても解決しない場合はマージせず、issueとPRの両方に状況を説明するコメントを残し、次回の実行に持ち越す）。
     f. 自動マージしてよいのはCIが検証する範囲（`npm test`・typecheck・lint等）に限る。法令根拠の正確性や業務判断そのものはCIでは検証できないため、実装前の時点でe-Gov等の一次資料を確認できない判定ロジックは、そもそも実装せず（下記の「曖昧」区分として）コメントに留めること。CIが緑であることは「壊していないこと」の確認であり「内容が正しいことの保証」ではない点を常に意識する。
   - **曖昧・要確認、または発注者の業務判断・法的判断が必要なもの**（CLAUDE.mdの「変更してはならない前提」に触れるもの、例: ビルドレス構成の変更、外部へのデータ送信の追加、人手レビュー工程の省略等を含む要望。または法令根拠をe-Gov等の一次資料で確認できない判定ロジックの要望）: 実装せず、確認したい点や実装しない理由をissueにコメントする。推測で実装しない。
   - **対象外の要望、またはやるべきでない要望**（人手レビュー工程の自動化・省略、自動提出・自動押印機能の追加、外部への通信の追加等、CLAUDE.mdの譲れない前提に反するもの）: 実装せず、本プロジェクトの制約に合わない理由をコメントする。
3. issueやPRを自分でクローズしない（マージによってGitHubが自動でissueをクローズするのは問題ない）。force-pushしない。`--delete-branch` でマージする対象以外のブランチを削除しない。

## 全般

- 変更をpushする前は必ずCLAUDE.mdの方針どおり `npm test`・`npm run typecheck`・`npm run lint` を通すこと。
- コミットメッセージ・PR説明文・コードコメントは既存のコードベースと同じ日本語の文体・用語で統一すること。
- 対応すべきものが何もない場合（オープンなissue・PRが無い、またはすべて対応済みの場合）は、その旨を簡潔に述べるだけでよい。作業を無理に作り出さないこと。
- 最後に、何を見つけて何をした（またはしなかった、その理由）かを簡潔に要約すること。
