# 要件定義書 — BtoB下請けケース管理ポータル

version: 0.1 / 2026-09 作成
対象: kensetsu-kyoka-toolkit の拡張（許認可自動化コアの周辺ツールとしての新規実装）

## 0. 本書の位置づけ

本書は、これまでの3モジュール（建設業許可・古物商許可・産業廃棄物収集
運搬業許可。いずれも「許可種別を判定・書類生成する」アドオン）とは
性質が異なる開発を対象とする。事業提案の柱（A）「補助金・許認可書類
作成のBtoB下請け」、すなわち**他の行政書士から仕事を受注する側の業務**を
支援するケース管理ツールである。

許認可の要件判定（`src/core/eligibility/`）は本開発の対象外であり、
コアが提供する「docx共通ヘルパー」「クライアント永続化」「リマインド
レジストリ」のうち、書類生成・リマインドの部分のみを再利用する。
開発環境構築・コーディング規約・Git運用は既存の`docs/DEVELOPMENT_GUIDE.md`
を適用する。

## 1. プロジェクト概要

### 1.1 背景

事業提案の柱（B）（定型許認可の自動化）はここまで3件のモジュールとして
具体化してきたが、柱（A）（BtoB下請け）はまだソフトウェアとして
何も着手していない。下請けとして案件を受注する場合、①どの元請
行政書士から、②いつまでに、③いくらで、④どのような許可種別の
書類作成を請け負っているか、という受注案件の管理が煩雑になりやすい
（特に複数の元請から同時に案件を受ける場合）。副業として限られた
時間で運用する以上、受注管理自体を自動化・省力化しておくことが、
柱（A）の事業を継続的に回すための前提になる。

### 1.2 目的

1. 元請行政書士（下請け元）ごとの案件一覧・進捗ステータスを管理する
2. 案件ごとの見積書・請求書のサマリーをdocxで生成する
3. 納期のリマインドを、既存のリマインドエンジンに統合する

### 1.3 重要な制約

- 本ツールが扱う「案件」は、あくまで下請けとして受注した書類作成
  業務の管理情報であり、最終的な許可申請の名義人（元請行政書士の
  顧客）本人の詳細な個人情報を必要以上に保持しないこと。案件レコードは
  「元請行政書士名」「案件の種別（許可種別等）」「納期」「報酬」を
  基本とし、顧客の氏名等は元請行政書士側で管理される前提とする
  （NFR-U2参照）
- 元請行政書士との業務委託契約・秘密保持契約（NDA）の内容によっては、
  ツールでの案件情報の記録方法自体に制約が生じうる。契約内容を
  必ず確認したうえで運用すること
- 既存のNFR-4（顧客の個人情報・財務情報を外部送信しない）を、
  「元請行政書士から預かった情報」にも適用する

## 2. 用語集

| 用語 | 説明 |
|---|---|
| 元請行政書士 | 本ツールの利用者（発注者）へ書類作成業務を下請けに出す、別の行政書士・行政書士法人 |
| 案件 | 元請行政書士から受注した、書類作成業務の単位 |
| ステータス | 案件の進捗段階（受付／作業中／納品待ち／完了／保留） |

## 3. 想定利用者・利用シーン

- 主利用者: 発注者本人（行政書士登録後、下請け業務の受注管理に使用）
- 想定シーン: 元請行政書士から新規案件の依頼を受ける →
  案件を登録（元請・種別・納期・報酬）→ 作業中はステータスを更新 →
  見積書・請求書のサマリーをdocxで生成し元請へ送付 → 納品後、
  ステータスを完了に更新

## 4. 機能要件

### 4.1 案件管理

| ID | 内容 | 備考 |
|---|---|---|
| FR-U1.1 | 元請行政書士（`PartnerRecord`）を登録・一覧表示できること | 会社名・担当者名・連絡先を保持する |
| FR-U1.2 | 案件（`CaseRecord`）を、どの元請行政書士からの依頼かに紐づけて登録できること | `partnerId`で`PartnerRecord`を参照する |
| FR-U1.3 | 案件には、案件名・許可種別（自由記述または既存の`licenseCategory`一覧から選択）・受注日・納期・報酬額・ステータスを記録できること | |
| FR-U1.4 | 案件のステータスを更新できること（受付→作業中→納品待ち→完了、または保留） | ステータス遷移に厳密な制約は設けず、任意の順で変更可能とする（実務上、差し戻し等で逆順の変更もありうるため） |
| FR-U1.5 | ステータス別・納期の近い順に案件を一覧表示できること | 既存のリマインド一覧表示（`REMINDER_RANGES`・`bucketizeAlerts`）と同様の考え方を、案件の納期に適用する |

### 4.2 見積書・請求書生成

| ID | 内容 | 備考 |
|---|---|---|
| FR-U2.1 | 案件情報から見積書のサマリーをdocxで生成できること | コアの`buildLabeledTable`・`buildDisclaimerParagraph`等を再利用する |
| FR-U2.2 | 案件情報から請求書のサマリーをdocxで生成できること | 同上。「これは正式な請求書ではなくサマリーである」旨の注記は不要（見積書・請求書は元々「正式様式」という概念がないため。既存様式群の免責注記パターンとは目的が異なる点に注意） |
| FR-U2.3 | 複数案件をまとめた「月次請求サマリー」（1つの元請行政書士に対する当月完了分の一覧）を生成できること | ✅ 2026年9月実装済み（`documents/monthlySeikyusho.js`）。「当月完了分」は`CaseRecord.completedDateIso`で判定する（`dueDateIso`は予定日のため使わない） |

### 4.3 納期リマインド（コアへの統合）

| ID | 内容 | 備考 |
|---|---|---|
| FR-U3.1 | 案件の納期を、既存のリマインドエンジン（`bucketizeAlerts`の5区分）で他の許可種別のリマインドと同じ一覧に統合表示できること | ライセンス（許可）ではなく「案件」を対象にするため、`registerScheduleFn`のレジストリパターンをそのまま流用するのではなく、`CaseRecord`から直接`ReminderAlert`相当を生成する専用の集計関数を用意する（設計書で詳細化） |
| FR-U3.2 | 納期超過の案件は、一覧の最上位（期限超過区分）に表示されること | 既存の`bucketizeAlerts`のロジックをそのまま適用できることの確認 |

### 4.4 インテイク

既存と同様、CLI/スクリプト操作を前提とする。Web一覧表示（`src/web/`
の拡張）は任意（4.6節）。

### 4.5 非機能要件

| ID | 内容 |
|---|---|
| NFR-U1 | 既存NFR-1〜7・NFR-C1〜C3を継承する |
| NFR-U2 | 案件レコードに、元請行政書士の顧客（最終依頼者）の氏名・連絡先等の詳細な個人情報フィールドを設けないこと（1.3節の制約を実装レベルで担保する） |
| NFR-U3 | 元請行政書士ごとの案件情報は、他の元請行政書士の情報と混同されないこと（`partnerId`による厳密な紐付けをテストで担保する） |

### 4.6 スコープ外（本フェーズで対応しないこと）

- オンライン決済・入金管理機能
- 元請行政書士側とのポータル共同編集（本フェーズは発注者単独での利用）
- 請求書の郵送・メール送信の自動化（既存のmailto下書き生成〈ADR-0004〉と
  同じ考え方で、送信自体は本人が行う）
- Webフォームでの案件登録・閲覧（CLI/スクリプトが前提。将来拡張候補）

## 5. 受け入れ基準

1. `npm test` が既存分＋新規追加分すべて成功すること
2. 既存モジュール（建設業許可・古物商許可・産廃・民泊）の出力・挙動が
   変化しないこと（回帰テスト）
3. 元請行政書士・案件をダミーデータで登録し、見積書・請求書サマリーの
   docx生成、納期リマインドの一覧表示ができること
4. 納期超過の案件が、既存のリマインド一覧の「期限超過」区分に
   正しく分類されること

## 6. 前提条件・依存事項

- 実際に下請け業務を受注する見込みの元請行政書士との契約条件
  （NDA・報酬体系等）が、本ツールでの案件情報の記録方法と矛盾しないか
  事前に確認すること
- 見積書・請求書のフォーマット（発注者の屋号・振込先情報等）を
  発注者から共有を受けること
