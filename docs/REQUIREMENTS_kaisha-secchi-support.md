# 要件定義書 — 会社設立サポートモジュール

version: 0.1 / 2026-09 作成
対象: kensetsu-kyoka-toolkit の拡張（許認可自動化コアの周辺ツールとしての新規実装。許可レジストリを使わない非許可モジュール）

## 0. 本書の位置づけ

本書は、これまでの許可種別アドオン5件（建設業許可・古物商許可・産業廃棄物
収集運搬業許可・住宅宿泊事業〈民泊〉届出・在留資格「技術・人文知識・
国際業務」申請支援。いずれも「許可種別を判定・書類生成する」アドオン）
とも、非許可モジュールの先行例である`docs/REQUIREMENTS_uketsuke-portal.md`
（BtoB下請けケース管理ポータル）とも性質が異なる開発を対象とする。

会社設立サポートは「許可の可否を判定する」業務ではなく、株式会社・
合同会社の設立に際して必要な**定款その他書類の作成支援**を行う業務である。
許認可の要件判定（`src/core/eligibility/`）は本開発の対象外であり、
コアが提供する「docx共通ヘルパー」のみを再利用する。案件の永続化・
スケジュール管理の設計は、同じく許可レジストリ（`registerScheduleFn`）を
使わない独立した業務ドメインとして設計された`docs/DESIGN_uketsuke-portal.md`
を構成・文体の直接の手本とする。

開発環境構築・コーディング規約・Git運用は既存の`docs/DEVELOPMENT_GUIDE.md`
を適用する。本書と対をなす技術設計書は`docs/DESIGN_kaisha-secchi-support.md`
（今回新規作成分）。

## 1. プロジェクト概要

### 1.1 背景

kensetsu-kyoka-toolkitはこれまで、①定型許認可の自動化（建設業・古物商・
産廃・民泊・在留資格の5モジュール）、②BtoB下請けの案件管理（受注管理・
見積書請求書生成）という2つの方向に展開してきた。会社設立支援は
行政書士の業務としては定番分野の一つであり、特に「許可取得を前提に
新規に法人を設立したい」という顧客層（例えば産廃許可や古物商許可を
法人として取得したい依頼者）にとっては、会社設立と許認可取得が
一連の依頼になりやすい。既存の許可アドオン群とのクロスセルの起点にも
なり得る分野であるため、今回新たにモジュール化を検討する。

会社設立支援は、古物商許可等の「許可の可否を法令の要件に照らして
判定する」業務とは性質が根本的に異なる。会社の設立自体に監督官庁の
「許可」は存在せず、定款を作成し公証人の認証（株式会社の場合）を経て、
出資を履行し、法務局に設立登記を申請すれば足りる。したがって本モジュールは
既存の要件判定エンジン（`src/core/eligibility/`）を一切使わない、
「書類生成とスケジュール管理」に特化したモジュールとして設計する。

### 1.2 目的

1. 株式会社・合同会社の設立に必要な定款の記載内容サマリーをdocxで生成する
2. 定款認証手続きの取次ぎ（株式会社の場合）を見据えた準備状況を管理する
3. 発起人決定書等、定款に付随する書類の生成を支援する
4. 定款認証予約日・出資金払込期限等、設立準備の主要な日程をシンプルに
   リマインドする

### 1.3 重要な制約（司法書士との職域境界）

会社設立サポートモジュールの設計において最も重要な制約は、**行政書士と
司法書士の業務範囲の境界線**である。これを誤ると無資格・無権限での
業務提供（他士業の独占業務侵害）につながるため、本書で明確に線引きする。

**行政書士が対応できる業務（本モジュールの対象）:**

- 定款の作成・作成代理（行政書士法上の「権利義務又は事実証明に関する
  書類」の作成に該当する）
- 公証役場における定款認証手続きの取次ぎ（嘱託人本人または代理人としての
  対応。電子定款化を含む）
- 発起人決定書・発起人全員の同意書等、定款に付随する書類の作成
- 会社設立後に必要となる税務署・都道府県税事務所・市区町村・年金事務所等
  への届出書類の作成（本フェーズでは対象外。9章「今後の拡張ポイント」参照）

**行政書士が対応できない業務（本モジュールの対象外・スコープ外）:**

- **設立登記の申請そのもの。** 登記申請書の作成・提出代理は司法書士法
  第3条・第78条（司法書士法人を含む）に定める司法書士の独占業務であり、
  行政書士が報酬を得て行うことはできない（無資格で行った場合、司法書士法
  第73条違反となりうる）
- 登記申請書・登記すべき事項を記録した記録媒体（CD-R等）・就任承諾書
  （設立登記添付書類としての様式）等、登記申請そのものに用いる書類の作成
- 法務局への登記完了確認・登記簿謄本の取得代理

したがって本モジュールは、**定款その他の付随書類のドラフト生成と、
設立準備の日程管理までを担い、出資金の払込が完了した時点で「司法書士へ
書類一式を引き継ぐ」ことを前提としたワークフローとして設計する**（4.3節・
設計書5章参照）。システムが生成する書類に「登記申請書」あるいはそれに
類する様式を一切含めないことを、実装上の明確な歯止めとする。

その他の既存の制約も継承する。

- 行政書士登録が完了するまで、本ツールを使って有償で書類作成・手続取次を
  行うことはできない（既存の`docs/REQUIREMENTS.md` 1.3節と同じ制約）
- 本システムが生成する定款・付随書類は、あくまで内容確認用の
  「ドラフト・サマリー」であり、公証人による認証・法務局による登記の
  完了を保証するものではない。UIやドキュメント上の文言でもこの前提を
  誤解させる表現をしないこと
- 定款の絶対的記載事項・認証手続き・費用等は法令改正・実務運用の変更が
  ありうるため、実装前に一次資料（法務省・日本公証人連合会等の公式情報）
  で最新の内容を確認すること（7章参照）

## 2. 用語集

| 用語 | 説明 |
|---|---|
| 発起人 | 株式会社の設立を企画し、定款に署名（記名押印）する者。1名以上出資する |
| 社員（合同会社） | 合同会社の出資者であり、原則として全員が業務執行権を持つ（持分会社共通の用語で、雇用契約上の「社員＝従業員」とは異なる） |
| 定款 | 会社の目的・組織・活動等に関する根本規則を定めた書面。会社の「憲法」に相当する |
| 絶対的記載事項 | 定款に必ず記載しなければならず、記載を欠くと定款自体が無効となる事項（3.2節参照） |
| 相対的記載事項 | 定款に記載しなければ効力を生じないが、記載自体は任意の事項（例: 現物出資、公告方法） |
| 任意的記載事項 | 定款外で定めても有効だが、明確化のため定款に記載する事項（例: 事業年度） |
| 定款認証 | 株式会社等の定款について、公証人がその成立の適法性を証明する手続き。合同会社等の持分会社では不要（1.3節・4.1節） |
| 出資の履行（払込） | 発起人・社員が引き受けた出資額を金銭で払い込む、または金銭以外の財産を給付すること |
| 発起設立 | 発起人が設立時発行株式の全部を引き受ける、株式会社設立方式の一つ（募集設立は対象外。4.6節） |
| 設立登記 | 法務局に対して行う、会社の法人格を発生させるための登記申請。**司法書士の独占業務（1.3節）** |
| 発起人決定書 | 定款で定めなかった事項（本店の具体的な所在場所・設立時代表取締役の選定等）を発起人の決定として書面化したもの |

## 3. 想定利用者・利用シーン

- **主利用者**: 発注者本人（行政書士登録後、自身の業務で使用する）。
  既存の許可アドオン群と同じ利用者・同じ運用形態
- **想定シーン**: 顧客（法人を設立したい個人）から事業内容・出資者構成
  等をヒアリングし、本システムに入力 → 定款ドラフト（サマリー）を生成 →
  発注者本人・依頼者が内容を確認・修正 → 正式な定款へ清書 →
  （株式会社の場合）公証役場への認証予約・持参物の準備 → 出資金払込の
  期限管理 → **司法書士へ定款・発起人決定書等の書類一式を引き継ぎ、
  設立登記は司法書士に依頼する** → 登記完了の連絡を受けて案件を完了とする
- 本フェーズでは、既存の建設業許可等と同様、顧客が直接システムを操作する
  フォームは対象外とし、発注者本人がデータを入力・実行するCLI/スクリプト
  操作を前提とする（`src/web/`の対応は本フェーズの対象外。4.6節）

## 4. 機能要件

### 4.1 定款作成支援

| ID | 内容 | 備考 |
|---|---|---|
| FR-I1.1 | 会社形態（株式会社／合同会社）を選択して定款作成データ（`TeikanInput`）を入力できること | 設計書3章。会社形態により以降の項目・手続きが分岐する |
| FR-I1.2 | 定款の絶対的記載事項を漏れなく入力でき、未入力項目がある場合は生成時に警告できること。株式会社は会社法第27条の5項目（目的、商号、本店の所在地、設立に際して出資される財産の価額又はその最低額、発起人の氏名又は名称及び住所）、合同会社は同法第576条の**6項目**（目的、商号、本店の所在地、社員の氏名又は名称及び住所、**社員が無限責任社員又は有限責任社員のいずれであるかの別**、社員の出資の目的及びその価額又は評価の標準）である点に注意すること | **【e-Gov法令検索で確認済み・2026年9月】** 当初「両形態とも5項目」としていたが誤り。合同会社は第576条第1項第5号（無限責任社員/有限責任社員の別）が株式会社側に対応項目のない追加事項であり、6項目になる。ただし合同会社の場合、同条第4項により「社員の全部を有限責任社員とする旨」に内容が固定されるため、定型文として自動的に記載すればよい（設計書3.1節・4.2節参照） |
| FR-I1.3 | 入力データから、定款の記載内容サマリーをdocxで生成できること | 既存の`buildDisclaimerParagraph`・`buildLabeledTable`等コア共通ヘルパーを再利用し、「正式な定款ではなく内容確認用のサマリーである」旨を明記する |
| FR-I1.4 | 会社形態が株式会社の場合と合同会社の場合とで、生成される定款サマリーの項目構成を切り替えられること | 合同会社は定款認証が不要であるため認証関連の案内文言を含めず、また株式会社特有の項目（発行可能株式総数・公告方法等）を出力しないこと（4.4節） |
| FR-I1.5 | 発起人（社員）を複数名登録でき、各人の出資額の合計が「設立に際して出資される財産の価額」と整合しているかを確認できること | 不整合の場合は警告に留め、生成自体は妨げない（要件判定エンジンのような合否判定は行わない。1.1節） |

### 4.2 付随書類生成

| ID | 内容 | 備考 |
|---|---|---|
| FR-I2.1 | 株式会社の場合、発起人決定書（本店の具体的所在場所・設立時代表取締役の選定等）の記載内容サマリーをdocxで生成できること | 定款に記載しなかった事項がある場合のみ対象。定款に全て記載済みの場合は生成不要である旨を案内する |
| FR-I2.2 | 各書類生成モジュールは、同一の入力データ（`TeikanInput`・`IncorporationCaseRecord`。設計書3章）から必要な項目を取り出して生成できること。書類ごとに二重入力させない設計にすること | 既存の`ApplicantProfile`共有パターンを踏襲 |
| FR-I2.3 | 生成した書類一式（定款サマリー・発起人決定書サマリー）を、司法書士への引継ぎ用としてまとめて出力できること | 任意機能。優先度はFR-I1・FR-I2.1より低い。ファイル一式のzip化等の実装方法は設計者の裁量とする |

### 4.3 スケジュール管理（コアへの統合を行わない）

会社設立の準備には「定款認証の予約日」「出資金払込の期限」という、
発起人自身が定める期日が存在する。これらは古物商許可の「更新」のような
法定の反復サイクルではなく、案件ごとに一度だけ発生する単発の期日である
ため、既存のリマインドレジストリ（`registerScheduleFn`。`LicenseEntry`を
前提とした契約）を流用せず、`docs/DESIGN_uketsuke-portal.md`と同じ考え方で
専用の集計関数を用意する（設計書5章）。

| ID | 内容 | 備考 |
|---|---|---|
| FR-I3.1 | 定款認証の予約日（株式会社のみ）を記録し、既存のリマインド表示ロジック（`bucketizeAlerts`）と同形式で一覧表示できること | 合同会社の案件では対象外（該当日付が無いため自動的にリマインド対象から外れる） |
| FR-I3.2 | 出資金払込の期限日を記録し、同様に一覧表示できること | 払込期限は発起人が定款または発起人の決定で定めた任意の期日であり、システム側で自動計算はしない（法定の起算日が無いため） |
| FR-I3.3 | 払込期限を過ぎても払込完了の記録がない案件は、期限超過区分に表示されること | 既存の`bucketizeAlerts`のロジックをそのまま適用できることの確認 |
| FR-I3.4 | 設立登記の申請自体はスコープ外（1.3節）であるため、登記期限そのものを計算・リマインドする機能は設けないこと。ただし、払込完了後は速やかに司法書士へ書類を引き継ぐ必要がある旨を、案内文言として画面・生成書類に含めてよい | 会社法上、設立登記は出資履行後2週間以内が目安とされるが、この期限管理自体は司法書士の職域における実務であるため、本システムでは「登記申請の期限管理」を行わず、あくまで「引継ぎを急ぐべき」という注意喚起に留める（誤って登記期限管理まで担っていると誤解されないようにするため） |

### 4.4 会社形態による差異の取り扱い

| ID | 内容 | 備考 |
|---|---|---|
| FR-I4.1 | 合同会社を選択した場合、定款認証に関する案内・入力項目（認証予約日等）を一切表示・要求しないこと | 合同会社を含む持分会社は定款認証が不要（会社法上、公証人による認証の対象外）であるため |
| FR-I4.2 | 会社形態に応じて、定款サマリーの項目名（例: 「発起人」→「社員」、「設立時発行株式数」の要否）を切り替えること | 用語を誤って混用すると定款として不正確な文書になるため重要 |

### 4.5 インテイク（入力）

既存と同様、CLI/スクリプト操作を前提とする。Web一覧表示（`src/web/`
の拡張）は任意（4.6節）。

### 4.6 非機能要件

| ID | 内容 |
|---|---|
| NFR-I1 | 既存NFR-1〜7・NFR-C1〜C3（`docs/DESIGN_kobutsu-core.md`前提）を継承する |
| NFR-I2 | 本モジュールは、`src/core/eligibility/`（要件判定エンジン）・`src/core/reminders/scheduleTypes.js`（許可レジストリ）のいずれにも依存しないこと。依存した場合、許可を前提としないモジュールという設計方針（1.1節）に反するため、コードレビューで確認する |
| NFR-I3 | 本システムが生成する書類一式に、登記申請書またはそれに類する様式（就任承諾書〈登記添付書類としてのもの〉・登記すべき事項の記録媒体等）を一切含めないこと（1.3節の職域境界を実装レベルで担保する） |
| NFR-I4 | 会社形態（株式会社／合同会社）の別を誤って混同した書類が生成されないよう、`TeikanInput.companyType`に応じた分岐をテストで担保すること |

### 4.7 スコープ外（本フェーズで対応しないこと）

- 設立登記の申請書類の作成・提出代理（1.3節。司法書士の独占業務）
- 募集設立（発起人以外からも出資者を募る設立方式）。本フェーズは発起設立のみ対象
- 株式会社以外の機関設計（取締役会設置会社・監査役設置会社等）の詳細な
  定款条項生成。本フェーズは取締役会非設置・小規模な発起設立を主対象とする
- 一般社団法人・NPO法人等、株式会社・合同会社以外の法人形態
- 会社設立後の税務署・都道府県税事務所・市区町村・年金事務所等への
  届出書類の作成（9章「今後の拡張ポイント」参照）
- 現物出資・種類株式・種類株主総会など、定款の相対的記載事項のうち
  高度な設計を要する項目の自動生成
- 電子定款の電子署名付与そのものの自動化（電子定款化の要否案内までを
  対象とし、実際の署名付与ツールの操作は対象外）
- Webフォームでの案件登録・閲覧（CLI/スクリプトが前提。将来拡張候補）

## 5. 受け入れ基準

1. `npm test`が既存分＋新規追加分すべて成功すること
2. 既存モジュール（建設業許可・古物商許可・産廃・民泊・在留資格・
   BtoB下請けポータル）の出力・挙動が変化しないこと（回帰テスト）
3. 株式会社・合同会社それぞれのダミーデータで、定款サマリーのdocx生成が
   でき、会社形態に応じて項目構成（認証関連案内の有無等）が正しく
   切り替わることを確認できること
4. 株式会社のダミーデータで発起人決定書サマリーのdocx生成ができること
5. 定款認証予約日・払込期限のダミーデータから、既存のリマインド表示
   ロジックと同形式の一覧が生成でき、期限超過の案件が正しく分類される
   こと（4.3節）
6. 生成される書類一式に登記申請書相当の様式が一切含まれないこと（NFR-I3）
   を目視・コードレビューの両面で確認できること
7. `src/core/eligibility/`・`src/core/reminders/scheduleTypes.js`への
   依存が無いこと（NFR-I2）をコードレビューで確認できること

## 6. 前提条件・依存事項

- 定款の絶対的記載事項・認証手数料・登録免許税等の金額・要件は法改正や
  運用変更がありうるため、実装着手前に法務省・日本公証人連合会等の
  一次資料で最新の内容を発注者・開発者双方で確認すること
- 本モジュールが生成した書類一式を実際に引き継ぐ提携司法書士（または
  発注者が案内する司法書士）の確保・連携方法は、本開発の対象外であり、
  発注者側の営業活動・提携関係構築に依存する
- 定款・発起人決定書の正式な書式・記載例（発起人全員の署名欄・実印押印欄
  等の体裁）は、発注者側の確認を経てから実装に反映すること
- 本プロジェクトは既存と同じGitHubリポジトリ`satou-aaaaa/sandbox`で管理する
