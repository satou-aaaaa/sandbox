# 0011. ミューテーションテスト（Stryker）とProperty-based testing（fast-check）の導入

Status: Accepted
Date: 2026-09-16

## Context（背景）

`npm run test:coverage`（行・分岐カバレッジ）は「そのコードが実行されたか」
しか示さない。実行されていても、テストのassertが緩ければバグを見逃す
（例: `>=` を `>` に書き換えても既存テストが気づかない、日付計算の月インデックスの
符号を反転しても既存テストの数値がたまたま一致してしまう、等）。2026年9月の
分岐カバレッジ拡充（`CHANGELOG.md`「テストパターンの網羅的拡充」）で
93.36%→99.17%まで引き上げたが、これはあくまで「実行されたか」の指標であり、
「テストの検証精度」そのものを測る指標ではないという限界が残っていた。

発注者から「ミューテーションテストといった、さまざまなテスト方法についても
調査し、導入」する依頼があり、`docs/DESIGN.md` 7章の既存テスト方針
（`node --test`によるユニットテスト中心、外部テストフレームワーク非導入）を
補完する形で、以下2つの手法を調査・導入した。

## Decision（決定）

### 1. ミューテーションテスト: Stryker Mutator

`@stryker-mutator/core`を開発依存として追加し、`stryker.config.mjs`で設定する。

- **テストランナー**: `command`ランナー（`node --test`をそのまま実行し、
  終了コードで成否を判定する汎用ランナー）を使う。本プロジェクトは
  ビルドレス構成（TypeScriptコンパイルなし）で`node:test`を使っており、
  Stryker公式のJest/Vitest/Mocha等の専用ランナー統合が使えないため。
  トレードオフとして`coverageAnalysis: "off"`が必須になり、ミュータント
  1件ごとに全テストを再実行するため実行時間が長い（数分〜数十分）。
- **対象範囲**: 要件判定・欠格事由判定・日付/金額計算・CSV相互変換など
  「間違えると実害が大きい」ロジックに絞り、書類生成（docx行組み立て）・
  Webページ表示は対象外とした（全ソース対象では2007ミュータント・
  実行1時間超と非現実的だったため。詳細は`stryker.config.mjs`のコメント参照）。
- **既知の非互換への対応**: `typescript@7`系で`ts.parseConfigFileTextToJson`が
  削除されており、Stryker（9系・10系とも）がこのAPIを呼ぶtsconfig.json
  前処理でクラッシュする既知の問題があるため、`tsconfigFile`に存在しない
  パスを指定して前処理自体をスキップする回避策を適用した。
- **実行方針**: `npm run test:mutation`として用意するが、CI（GitHub Actions）
  には組み込まない。実行時間が長くPRごとの自動実行に向かないため、
  大きな変更の節目やテスト方針の見直し時に手動実行する運用とする。

### 2. Property-based testing: fast-check

`fast-check`を開発依存として追加し、既存の具体例ベースのテストファイル
（`test/dateUtils.test.js`・`test/clientCsv.test.js`・`test/htmlUtils.test.js`）に
「性質」ベースのテストを追加した。専用のテストファイルには分離せず、
既存ファイルの末尾に追記する形にした（1モジュール1ファイルの既存方針を維持）。

対象は「入力の組み合わせが実質無限にあり、かつ満たすべき性質を明確に
言語化できる」純粋関数に限定した（乱用すると通常のテストより読みにくくなるため）:
`daysUntil`（反対称性・反射性・実カレンダーとの整合性）、
`clientsToCsv`/`clientsFromCsv`（往復性）、`escapeHtml`（XSS対策の本質的性質）。

## Consequences（影響）

- **メリット**: 導入初回の実行で、`dateUtils.js`の`parseIsoDate`（月インデックス
  計算）と`toIsoDate`（`daysUntil`の基準日省略時のフォールバック。実際の
  `npm run reminders`・`/reminders`画面が常用する既定動作）の2箇所で、
  既存の具体例ベーステストでは検出できなかった生き残りミュータントが
  即座に見つかった。両者とも実際にテストを追加して解消済み。
  Property-based testingの`clientsToCsv`↔`clientsFromCsv`往復テストは、
  制御文字・サロゲートペア等を含む300パターンをその場で生成して初回から
  成功し、CSV相互変換の実装が特殊文字に対して堅牢であることを裏付けた。

  対象範囲（要件判定・欠格事由判定・日付/金額計算・CSV相互変換。24ファイル・
  1030ミュータント）での初回実行のミューテーションスコアは75.24%
  （killed 723・timeout 52・survived 255）。生き残ったミュータントを分析した
  結果、特に「間違えると実害が大きい」5法定要件の判定ロジックで見過ごせない
  弱点が見つかった:
  - `zaisanKiso.js`（財産的基礎）: 特定建設業の3条件判定
    （`deficitRatio<=20 && currentRatio>=75 && (capitalAmount>=2000万 && netAssets>=4000万)`）の
    比較演算子・論理演算子を書き換えても、既存テストが「3条件すべて満たすケース」
    「AND条件がORに壊れていないか」を検証していなかったため気づけなかった
    （44.59%→77.03%に改善）
  - `keieiGyomuKanri.js`（経営業務管理体制）: ルートD（複合要件）の4条件
    （役員等2年以上＋財務・労務・運営の補佐者各5年以上）のいずれか1つが
    基準未満でも合格してしまう書き換えを検出できていなかった
    （53.85%→71.79%に改善）
  - `senninGijutsusha.js`（専任技術者）: 学歴区分（高卒/大卒）の文字列比較を
    常にtrueに書き換えても、学歴区分が一致しないケースのテストが無く
    気づけなかった（73.47%→75.51%に改善）
  - `consistencyChecks.js`・`clientCsv.js`・`clientStore.js`でも、境界条件・
    複数レコード時の検索ロジック・ファイルI/Oエラー時の再送出等で同様の
    弱点を発見し、対応するテストを追加した
    （67.01%→70.10%、87.58%→92.16%、82.11%→89.47%にそれぞれ改善）

  上記6ファイルの改善により、対象範囲全体のミューテーションスコアは
  75.24%→約80.78%（推定。killed 790・timeout 42・survived 198）に向上した。
  残る生き残りミュータントの大半は、判定結果（`passed`/`eligible`）には
  影響しない人間可読な文言（`reasons`/`warnings`の具体的な文字列、`label`/`key`
  フィールドの値）の書き換えであり、実際にコード内でその値を検索・比較する
  箇所が存在しないことを確認した上で、意図的に対応を見送った
  （`npm test`が292件→321件に増加）。
- **デメリット**:
  - ミューテーションテストは実行時間が長く、対象範囲を絞る判断が必要
    （全ソース対象は非現実的）。対象範囲を絞ったことで、書類生成・Web表示側の
    アサーション精度はこの仕組みではカバーされない（branch coverageの
    拡充で個別に対応済みという前提に立っている）
  - Stryker・TypeScript間の既知の非互換に対する回避策（`tsconfigFile`の
    存在しないパス指定）は、公式なサポートではなく将来のバージョンアップで
    挙動が変わりうる暫定対応
  - fast-checkのproperty-based testingは、性質を正しく言語化できないと
    かえってテストの意図が読み取りにくくなる。乱用せず対象を絞る方針を
    維持すること
- **見直しのトリガー**: Stryker側でTypeScript 7系対応の公式な修正が
  リリースされた場合、`tsconfigFile`の回避策を見直す。ミューテーション
  テストの対象範囲は、書類生成・Web表示側で実際にバグが見逃された
  実績が出た場合に拡大を検討する。
