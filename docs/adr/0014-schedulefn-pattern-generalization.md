# 0014. リマインド計算のレジストリ契約（ScheduleFn）を変更せず4パターンに対応させる

Status: Accepted
Date: 2026-09-16

## Context（背景）

`docs/DESIGN_kobutsu-core.md`（M11）で導入した`registerScheduleFn`のレジストリ
契約（`ScheduleFn = (license: LicenseEntry) => ScheduleItem[]`）は、当初
建設業許可（満了日ベース・有効期間5年固定）と古物商許可（変更トリガー型）
の2パターンのみで設計されたものだった。その後、産廃許可・民泊届出・
技人国ビザの3モジュールを追加する過程で、この契約が想定していなかった
2つの新しいリマインドの性質が出てきた。

1. **産廃許可**: 有効期間が5年固定ではなく、施行令に基づき新規5年／更新時
   優良認定で7年、と可変になる（`docs/DESIGN_sanpai-core.md` 4.3節）
2. **民泊届出**: 期限が「許可日からの相対計算」ではなく、法令で定められた
   暦日（毎年2/4/6/8/10/12月15日）に固定され、報告実績・届出日に一切
   依存しない「暦日固定・反復型」になる（`docs/DESIGN_minpaku-core.md` 4.3節）
3. **技人国ビザ**: 在留期間が3月/1年/3年/5年と可変で、かつ許可日から満了日を
   一意に計算できない（更新のたびに次回期間が変わりうる）ため、「満了日
   そのもの」を直接入力として受け取る必要がある
   （`docs/DESIGN_gijinkoku-core.md` 4.3節）

いずれのケースでも、`ScheduleFn`の契約自体（`LicenseEntry`を1件受け取り
`ScheduleItem[]`を返す、今日の日付を引数に取らない）を変更する必要が
本当に無いのか、実装前に都度検証する必要があった。

## Decision（決定）

`ScheduleFn`契約は変更せず、各許可種別アドオン側の実装だけで4パターンすべてに
対応できることを確認した。

| パターン | 起点 | 例 |
|---|---|---|
| 満了日ベース（固定期間） | 許可日から固定期間後を計算 | 建設業許可（5年固定） |
| 変更トリガー型 | 変更・廃業という出来事の発生日 | 古物商許可 |
| 満了日ベース（可変期間） | 許可日から可変期間（引数化）後を計算 | 産廃許可（5/7年。`src/core/reminders/expirySchedule.js`に共通化） |
| 満了日直接入力（可変期間） | 満了日そのものを`<種別>Detail`に保持 | 技人国ビザ（在留カード記載の満了日） |
| 暦日固定・反復型 | 起点日に依存しない固定の暦日テーブル | 民泊届出（`new Date()`で本日を取得し、暦日テーブルを参照） |

対応方法は以下の2点に集約される。

1. **有効期間が可変な場合**: 満了日計算ロジック自体（月単位丸め処理）を
   `src/core/reminders/expirySchedule.js`へ切り出し、有効期間（年数）を
   引数化する（産廃許可の実装で追加。建設業許可の`calcRenewalSchedule`も
   これを呼ぶ薄いラッパーへ変更し、既存の出力値は変えていない）
2. **期限日自体が「今日」に依存して変わる場合**（暦日固定・反復型）:
   `ScheduleFn`は`today`を引数に取らないため、実装関数の内部で`new Date()`
   により本日を取得する。起点を「届出日」等の固定値にすると最初のサイクル
   から期限が進まなくなるバグになるため、`<種別>Detail`の日付フィールドは
   「リマインドが発生する条件」のゲートとしてのみ使い、期限日の計算自体は
   常に「本日」を基準にする（民泊届出の実装で判明した設計上の要点）

## Consequences（影響）

- **メリット**: `docs/DESIGN_kobutsu-core.md`で設計したレジストリパターンが、
  事前に想定していなかった2つの新しい性質（可変期間・暦日固定反復）にも
  コア側を変更せず対応できることが、3つの独立した実装を通じて実証された。
  今後4つ目以降の「満了日ベース（可変期間）」「暦日固定・反復型」の許可種別
  が出てきても、`expirySchedule.js`・「`new Date()`を関数内部で使う」という
  既存パターンをそのまま再利用できる見込みが高い
- **デメリット・トレードオフ**: 「期限日を`today`基準で計算する」設計は、
  `ScheduleFn`が純粋関数ではなくなる（同じ`license`を渡しても呼び出し日に
  よって結果が変わる）。この非純粋性はテスト時に`new Date()`をモックせず、
  `calcNextReportDeadline(baseDateIso)`のような内部の暦日計算関数を別途
  エクスポートしてテストする回避策で対処している（`test/minpakuPeriodicReportSchedule.test.js`参照）
- **見直しのトリガー**: 「暦日固定・反復型」の許可種別がもう1つ以上追加され、
  暦日テーブル参照ロジックに共通化できる部分が明確になった場合、
  `expirySchedule.js`と同様に`src/core/reminders/`へ切り出すことを検討する
  （`docs/DESIGN_minpaku-core.md` 7章で予告済み）
