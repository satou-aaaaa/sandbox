# 0018. 設計前提の機械検査と、運用ルーティンの拡充

Status: Accepted
Date: 2026-09-30

## Context（背景）

ADR-0017 で、Issueの自律処理（トリアージ→実装→AIレビュー→自動マージ→事後リバート）は整った。
一方で、次の領域は「誰も見ていない」状態だった。

- **設計前提の遵守**: `docs/DESIGN.md` 1章の前提（ビルドレス・外部送信なし・法令根拠の明記・
  DB無し）の検査が、AIレビュアーのプロンプト頼みで決定的でなかった。
- **法令・様式の改正**: 判定ロジックの根拠（e-Gov・所管官庁ページ）が変わっても検知する仕組みが無かった。
  本プロジェクトで最も実害の大きいリスク。
- **CIに入っていないテスト**: `test:mutation`・`test:bdd` は手動実行のみで、劣化に気づけない。
- **ドキュメントの陳腐化**、**運用レポートの死角**（承認待ちPRの滞留・メジャー更新の放置）、
  **リマインドの見落とし**、**押印前レビューの手間**、**新モジュール追加の定型作業**。

## Decision（決定）

次の10点を導入する。いずれも「判断は人が行い、検知・下書き・整理だけを自動化する」方針で、
自動押印・自動提出・法令ロジックの自動書き換えは行わない。

1. **設計前提ガード** `test/invariants.test.js`（`npm test` に含まれCIで実行）: `.ts`・トランスパイラ・
   `build` スクリプトの不在、`src/` にネットワーク送信APIが無いこと、Webサーバーの待受が
   `127.0.0.1` のみ、DBライブラリの不在、`data/` が未コミット、判定・期限計算ロジックの冒頭に根拠URLがあること。
   根拠URLは導入時に既存28ファイルで未記載だったため、基準線（`test/fixtures/legal-basis-baseline.json`）で許容したうえで、
   同日中に解消した（24ファイルは条文をe-Govで確認してURLを追記、4ファイルは法令に基づかないため理由つきで
   `legal-basis-exempt.json` に免除）。基準線は現在空で、新規は必須とする。
2. **法令・様式改正ウォッチャー** `scripts/law-watch.mjs`＋`.github/workflows/law-watch.yml`（週次）:
   冒頭コメントの根拠URLを取得し、本文の正規化ハッシュを `docs/law-watch-baseline.json` と比較して、
   変化・リンク切れを1件の常設Issueに集約する。更新は人が内容を確認してから基準線を更新するPRで行う。
   取得するのは**公開ページのみ**で、個人情報・財務情報は一切送信しない（前提2に抵触しない）。
3. **期限リマインドの日次点検** `npm run reminders:daily`: ローカルで期限を計算し、全文は `out/` に保存、
   標準出力には**件数と最短期限日のみ**を出す（クライアント名は出さない）。Gmail等への自動送信はしない
   （個人情報の外部送信になるため。ADR-0004 と同方針）。
4. **週次ミューテーションテスト** `.github/workflows/weekly-mutation.yml`: Stryker を回し、
   生き残ったミュータントをレポート（アーティファクト＋ジョブサマリー）にする。CIの必須チェックには含めない。
5. **夜間の受け入れテスト** `.github/workflows/nightly.yml`: `test:bdd`（`npm test` 外）を夜間に回し、
   失敗時は常設Issueへ集約する。E2E・負荷は既存のCIで実行済みのため重複させない。
6. **ドキュメント整合性チェック** `test/docsConsistency.test.js` と `npm run changelog:draft`:
   モジュールと設計書・要件定義書の対応、CLAUDE.mdのディレクトリ構成、ADR索引の欠落を検知し、
   CHANGELOGの下書きをgit履歴から作る（取り込みは人が編集して行う）。
7. **依存メジャー更新の事前検証**: メジャー更新のDependabot PRは、CIがそのPRのブランチで全テストを
   走らせること自体が隔離検証になる。運用レポートに「メジャー更新PRとCI結果」を載せ、人の判断材料にする。
8. **押印前レビューパック** `src/core/documents/reviewPack.js`: 判定の `reasons`/`warnings`・未充足・
   期限を1つのdocxにまとめる。最終レビューの入口を1枚にするための下書きで、合否は再計算しない。
9. **新モジュール雛形** `npm run scaffold:module`: src・test・docsの骨組みを作る。判定ロジックは作らず、
   法令根拠の位置に 法令根拠の未記入を示すTODO印 を置く（残っていると1のガードで失敗する）。
10. **PR/Issue滞留の監視**: 運用レポート（`agent/report.mjs`）に、承認待ちの日数が長いPR・Issueを載せる。

## Consequences（影響）

- 設計前提の違反が、レビューでなくCIで決定的に落ちる。免除リストは、法令に基づかない
  ファイルだけに理由つきで使う（安易に増やさない）。
- 法令ウォッチャーはページ本文のハッシュ比較のため、ページの軽微な改版でも「変化の可能性」として
  検知する（偽陽性あり）。人が差分を見て、基準線を更新するかロジックを直すかを判断する。
  国の公式サイトの構造変化・アクセス制限で取得できない場合は「取得失敗」として別掲する。
- ミューテーション・BDDは時間がかかるためCIの必須にはしない。閾値による自動失敗もしない
  （実測値がたまるまで、傾向を見るだけ）。
- 新しい定期workflowが増えるため、Actionsの利用時間を消費する（すべて `schedule` は週次〜夜間、
  Linux 1ジョブ）。負担が大きければ頻度を落とす。
- 見直しのトリガー: 偽陽性が多くIssueが読まれなくなった場合、ウォッチャーの正規化・対象を絞る。
