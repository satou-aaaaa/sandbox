# 0013. 負荷テスト・カオスエンジニアリング・契約テストの導入

Status: Accepted
Date: 2026-09-16

## Context（背景）

ADR-0012に続き、発注者から「負荷テスト・カオスエンジニアリング・契約テストに
ついても導入してほしい（今後、ローカルツールではなくなる可能性があるため）」
という依頼を受けた。これら3つは、ADR-0012の調査時点では「単一利用者の
ローカル実行ツール」という現在の性質上、価値が薄いとして対象外としていた
（ADR-0012 Context参照）。今回、発注者から「将来ローカル限定ではなくなる
可能性がある」という前提の変化が明示されたため、その前提のもとで意味のある
形に設計し直して導入した。

## Decision（決定）

### 1. 負荷テスト（autocannon）

[autocannon](https://github.com/mcollina/autocannon)を追加し、
`load/web-server.load.js`（`npm run test:load`）でインテイクフォームの
主要エンドポイント（`GET /`・`POST /submit`）に対して同時アクセス
（10コネクション・5秒間）を行う。現時点で具体的な性能要件（目標レイテンシ・
スループット）が存在しないため、厳密な閾値判定は行わず「同時リクエスト下で
エラー・タイムアウト・5xxが発生しないこと」の確認に留める。実測した
レイテンシ・スループットは`npm run test:load`実行時にコンソールへ出力され、
将来具体的な性能目標が定まった時点でアサーションを追加できる形にしてある。
CIでは他の「OS非依存」チェックと同じくubuntu-latest・Node22.xの1系統のみで
実行する。

### 2. カオスエンジニアリング（アプリケーション層の障害注入）

Chaos Monkey等の従来型カオスエンジニアリングツールは、Kubernetes等の
分散インフラを前提としており、単一プロセスのローカルツールという現状の
構成には適合しない。そこで`test/chaos.test.js`に、依存先（ファイルシステム）
の障害・同時実行の競合をアプリケーション層で直接注入するテストを追加した:

- 同時に複数の`upsertClient`/`upsertDraft`呼び出しが発生した場合の
  read-modify-write競合（lost update）
- ディスク書き込み失敗（`ENOSPC`を`node:test`の`mock.method`でシミュレート）
- クライアントデータファイルの破損（不正なJSON）

**このテストの作成過程で、実際に深刻なバグを発見した**: `clientStore.js`・
`draftStore.js`の`upsertXxx`系関数は、ファイル全体を読み込み→変更→
書き戻すread-modify-write方式で実装されており、ロック機構が無かったため、
2つの呼び出しがほぼ同時に発生すると、後から書き込んだ方が先の変更を
丸ごと上書きし、片方の登録が完全に失われることを確認した（`Promise.all`で
2クライアントを同時登録すると1件しか残らないことを再現）。単一利用者が
Webフォームを複数タブで操作した場合や、将来複数利用者が同時にアクセスする
ようになった場合に実際に発生しうる。

**対応**: `src/core/reminders/fileLock.js`を新設し、ファイルパスごとに
read-modify-write操作を直列化するプロセス内の簡易ミューテックスを実装した。
`clientStore.js`の`upsertClient`/`upsertClientLicense`/`removeClient`、
`draftStore.js`の`upsertDraft`/`removeDraft`をこのロックで包んだ。
複数プロセス・複数マシンからの同時書き込み（ファイルシステムレベルの
排他制御）は対象外とし、将来複数プロセス構成になった場合はデータベース
導入（ADR-0003の見直し）とあわせて再検討することとした。

### 3. 契約テスト（JSON Schema + ajv）

本ツールは外部のAPI消費者を持たないため、Pact等の消費者駆動契約テストを
導入する相手がいない。しかし将来`data/clients.json`の形（`ClientRecord`/
`LicenseEntry`。ADR-0008）をAPIとして公開する可能性を見込み、
`schemas/client-record.schema.json`（JSON Schema）としてこの形を明文化し、
[ajv](https://ajv.js.org/)で検証する`test/contract.test.js`を追加した。

- スキーマは`src/core/reminders/digest.js`のJSDoc型定義を実行時検証可能な
  形で複製したものであり、型定義を正とする（型定義変更時はスキーマ側も
  追従させる必要がある）
- 許可種別固有の追加フィールド（`kobutsuDetail`等）は、コアが許可種別を
  知らないという設計原則（docs/DESIGN_kobutsu-core.md）に従い、
  `licenseEntry`の`additionalProperties: true`で許容し、コア自体は規定しない
- 実際に`clientStore.js`で保存・読込したデータがスキーマに適合し続けることを
  確認する回帰テストを含む（実装とスキーマの乖離を検出する）
- 将来実際にAPIを公開する際は、このスキーマをOpenAPI定義やPactの契約定義に
  そのまま転用できる

## Consequences（影響）

- **メリット**:
  - カオステストの作成過程で、実際に顧客データが失われうる重大な競合状態
    バグを本番投入前に発見・修正できた。まさに「システムに障害を注入して
    弱点を見つける」というカオスエンジニアリングの狙い通りの成果
  - 契約テストにより、将来APIとして公開する際の土台となるデータ形状の
    定義が明文化された
  - 負荷テストにより、現状のシステムが同時アクセスに対して最低限の
    頑健性を持つことが確認できた
- **デメリット**:
  - `fileLock.js`はプロセス内限定のロックであり、複数プロセス・複数マシン
    構成への移行時には別の排他制御方式（データベースのトランザクション等）
    への置き換えが必要になる。「今のうちに直しておく」応急的な対応であり、
    恒久対応ではないことを認識しておく必要がある
  - `autocannon`の依存関係（`hyperid`→`uuid`）に既知の中程度脆弱性が
    1件ある（`npm audit --audit-level=high`のCIゲートには抵触しない。
    開発専用ツールであり本番コードには含まれないため実害は小さいと判断）
  - JSON Schemaによる契約テストは「型定義との二重管理」という保守コストを
    伴う。型定義（JSDoc）を変更した際にスキーマの更新を忘れるとテストが
    その乖離を検出するが、忘れずに追従させる運用上の注意が必要
- **見直しのトリガー**: 実際に複数プロセス・複数マシン構成への移行が
  具体化した時点で、`fileLock.js`をデータベースのトランザクション等へ
  置き換える。外部のAPI消費者（他システム）が実際に登場した時点で、
  `schemas/`のJSON SchemaをベースにPact等の消費者駆動契約テストへ
  発展させることを検討する。
