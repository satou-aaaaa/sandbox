# 0015. ScheduleFn契約の汎用性の実証を年次反復型・条件履行期限型の2パターンへ拡張

Status: Accepted
Date: 2026-09-17

## Context（背景）

[ADR-0014](0014-schedulefn-pattern-generalization.md)は、産廃許可・民泊届出・
技人国ビザの3モジュールを追加する過程で判明した2つの新しいリマインドの
性質（満了日ベース〈可変期間〉・満了日直接入力〈可変期間〉・暦日固定反復の
計3パターンを含む、既存の満了日ベース〈固定期間〉・変更トリガー型と合わせて
計5パターン）について、`registerScheduleFn`のレジストリ契約
（`ScheduleFn = (license: LicenseEntry) => ScheduleItem[]`）を変更せずに
対応できることを確認した。

ADR-0014の完了後、さらに2つのモジュールを追加する過程で、それぞれ別の
新しい起点パターンを持つリマインドが必要になった。

1. **経営事項審査（経審）申請支援**（`docs/DESIGN_keiei-jiko-shinsa-core.md`）:
   有効期限（審査基準日から1年7ヶ月）を切らさないために、直近の審査基準日
   から翌年の審査基準日を推定して反復する「年次反復型」が必要になった
   （`src/licenses/keiei-jiko-shinsa/reminders/annualCycleSchedule.js`）
2. **農地転用許可**（`docs/DESIGN_nouchi-tenyo-core.md`）: 農地転用許可には
   他の許可種別のような「更新（有効期限）」の概念が無く、代わりに許可証に
   個別記載された期限（工事着手期限・完了報告期限）を追跡する「条件履行
   期限型」が必要になった
   （`src/licenses/nouchi-tenyo/reminders/conditionDeadlineSchedule.js`）

ADR-0014と同様、いずれのケースでも`ScheduleFn`契約自体を変更する必要が
本当に無いのか、実装前に検証が必要だった。

なお、`docs/ARCHITECTURE.md`の実装当時の記述で、経審の「年次反復型」が
技人国ビザの「満了日直接入力型」（既に「第四のリマインドパターン」を
名乗っていた）と同じ「第4のリマインドパターン」を誤って重複して名乗って
しまっていた（実装順のクロスチェック漏れ）。本ADR作成時にあわせて
`docs/ARCHITECTURE.md`の該当箇所を「第5」「第6」に採番し直して修正した。

## Decision（決定）

`ScheduleFn`契約は変更せず、7パターン目までのリマインド方式に、各許可種別
アドオン側の実装だけで対応できることを確認した。ADR-0014の表に以下の2行を
追加する形で拡張する。

| パターン | 起点 | 例 |
|---|---|---|
| （ADR-0014の5パターン） | | |
| 年次反復型 | 固定された年次イベント（決算等）を起点に、有効期限を切らさないよう毎年反復して次回基準日を推定する | 経審（審査基準日から1年7ヶ月の有効期限を、直近の審査基準日から翌年分を推定して算出） |
| 条件履行期限型 | 許可証に個別記載された期限日をそのまま入力として受け取る。更新の概念自体が無く、履行済みフラグが記録されると自動的にリマインドが消える | 農地転用許可（工事着手期限・完了報告期限） |

対応方法は以下の2点に集約される（いずれもADR-0014で確立した2つの対応方針の延長線上にある）。

1. **年次反復型**: 「直近の基準日」を`<種別>Detail`の入力として受け取り、
   関数内部で「翌年の基準日 = 直近の基準日 + 1年」を計算するだけで済み、
   ADR-0014の対応方針1（有効期間の引数化）・方針2（`today`基準の計算）の
   いずれにも該当しない、より単純な「基準日の年次シフト」という3つ目の
   対応方法として整理できる
2. **条件履行期限型**: 期限日そのものを`<種別>Detail`に直接保持する点は
   ADR-0014の「満了日直接入力（可変期間）」パターン（技人国ビザ）と
   構造的に同じだが、技人国ビザが「更新のたびに新しい満了日を受け取る」の
   に対し、条件履行期限型は「履行済みフラグが立つとリマインド自体が
   消える（次の期限が発生しない）」という一方向・使い切り型の性質を持つ
   点が異なる。この違いも`ScheduleFn`側の実装（履行済みなら空配列を返す）
   だけで吸収でき、契約変更は不要だった

## Consequences（影響）

- **メリット**: ADR-0014で示した「レジストリ契約は変えず実装側で吸収する」
  という設計方針が、経審・農地転用許可という性質の異なる2モジュールでも
  再現性をもって成立することが実証された。7パターン目までの実績が蓄積した
  ことで、今後新しい許可種別・独立ドメインを追加する際も、まずこの
  7パターン（ADR-0014・本ADR参照）のいずれかに当てはまらないかを検討する
  という判断の出発点ができた（`CLAUDE.md`のコーディング規約からも参照）
- **デメリット・トレードオフ**: パターン数が増えるほど、`docs/ARCHITECTURE.md`
  の各モジュール節に埋め込まれた「第Nのリマインドパターン」という説明文が
  実装順への依存度を増し、本ADRで発生したような採番の重複・ズレが今後も
  起こりうる。パターン一覧の一次情報源はADR側（本ADRとADR-0014）に置き、
  `docs/ARCHITECTURE.md`側の「第N」という個別の採番表記は将来的に廃止し
  「ADR-0014・0015のNパターンのいずれか」という参照に統一することも
  検討の余地がある（本ADR時点では既存表記への影響が広いため見送り、
  新規追加分から`docs/ARCHITECTURE.md`更新時に本ADRを参照する運用に留める）
- **見直しのトリガー**: 8パターン目に相当する新しい起点パターンが必要に
  なった場合、ADR-0014・本ADRと同様に新しいADRを追加する（既存ADRの内容は
  書き換えない）
