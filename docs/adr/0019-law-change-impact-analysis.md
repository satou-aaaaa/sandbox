# ADR-0019: 法令改正の影響分析を段階的に導入する

- Status: Accepted
- Date: 2026-09-30

## Context（背景）

`scripts/law-watch.mjs`（ADR-0018）は、根拠URLの内容変化を検知し、変化したURLと「そのURLを根拠に挙げているソースファイル」を
常設Issueに集約する。しかし、人が次にやること（どの設計書・要件定義書を見直すか、改正のどこが変わったか）は手作業で、
行政書士業務の中核である「法令変更への追随」で最も時間がかかる部分が残っていた。

調査（2026-09-30）: e-Gov法令API v2（2025年3月公開・登録不要）は、法令本文と改正履歴を返す
（<https://laws.e-gov.go.jp/api/2/swagger-ui/>）。旧版との比較による条文単位の差分取得が技術的に可能。
一方、AIエージェントをCIに組み込む際は、外部由来の文字列（Issue/PR本文など）によるプロンプトインジェクションが
実際に問題になっている（Anthropic公式のsecurity-review Actionでの事例など）。

## Decision（決定）

三段階で導入し、**各段階とも判定ロジックの自動修正は行わない**（人手レビュー必須の前提を維持。法令領域は人手承認）。

1. **第一段（本ADRで実装）**: 決定論的な影響先の特定。根拠URLを挙げるファイルから、見直し対象の設計書・要件定義書を
   割り出してレポートに載せる（`impactedDocs`）。LLMは使わない。
2. **第二段（未実装）**: e-Gov法令API v2の改正履歴から、変更された条文を決定論的に抽出する。
3. **第三段（未実装）**: 読み取り専用フェーズ（`triage` 相当・Read/Glob/Grepのみ）のLLMが、差分の要約と
   見直しチェックリストを作る。入力に含まれる法令本文は外部由来のデータとして扱い（指示として解釈させない）、
   出力は起票文面のみ。起票は `agent-needs-human` 付きで、実装フェーズには回さない。

## Consequences（影響）

- 第一段だけで、変化の通知から「どの設計書を直すか」までの手作業が減る。外部通信・依存追加・LLM利用は増えない。
- 対応表は命名規則（`src/licenses/<名前>/` → `docs/DESIGN_<名前>-core.md` 等）に依存する。新モジュールが規則から外れると
  設計書が特定できない。`npm run scaffold:module` の規則と `test/docsConsistency.test.js` の対応検査が前提。
- 第二・三段は、実データでの精度と費用を見てから着手する。改正の解釈（判定ロジックへの影響の最終判断）は人が行う。
