# 0004. 更新リマインドの通知はメール自動送信ではなくmailto:下書きに留める

Status: Accepted
Date: 2026-09（M4）

## Context（背景）

`docs/PROPOSAL.md` のロードマップではM4を「更新リマインドのメール自動送付」
としていた。しかし実際にメールを自動送信するには、SMTPサーバーや
SendGrid等のメール配信APIといった外部サービスとの連携、および
そのための認証情報（APIキー等）の管理が必要になる。

これはNFR-2（追加の外部サービス・APIキー・クラウド環境を必須としない）・
NFR-4（顧客の個人情報を外部へ送信する処理を実装しない）と直接抵触しうる。
また `docs/DESIGN.md` 1章の設計原則1「人手レビューを唯一の必須ステップとして
残す」（自動送信・自動押印などを追加しない）とも関連する考え方である。

どの送信チャネルを使うか、外部サービスを許容するかは発注者
（本プロジェクトの場合は開発者自身）の意思決定事項であり、実装側で
勝手に選定すべきではないと判断した。

## Decision（決定）

実際のメール自動送信は実装しない。代わりに、クライアントに連絡先
メールアドレス（`ClientLicenseRecord.contactEmail`、任意）を登録できるように
した上で、期限が近いリマインドについて `mailto:` URL（件名・本文つき）を
生成する `buildReminderMailtoUrl` を実装した。CLI・Webフォーム双方から
このリンクを開くと、既定のメールソフトで下書きが開くだけで、本ツール自体が
送信することはない。件名・本文には「これは下書きである」旨を明記し、
送信前の内容確認を促す。

## Consequences（影響）

- **メリット**: 外部サービス・認証情報が一切不要。実装がシンプルで、
  ブラウザ/OS標準の `mailto:` 機能だけで完結する。人手による最終確認を
  必ず介在させられる（設計原則1との整合）
- **デメリット**: 複数件のリマインドを一括送信するような効率化はできない
  （1件ずつ下書きを開いて送る運用になる）。メールクライアントが
  設定されていない環境では機能しない
- **見直しのトリガー**: 管理するクライアント数が増え、1件ずつの手動送信が
  現実的な運用コストを超えた場合、SMTP等を使った自動送信機能の追加を
  改めて検討する。その際は本ADRをSupersedeする新しいADRを書き、
  選定した送信チャネル・認証情報の管理方法（`.env` 等）を明記すること
