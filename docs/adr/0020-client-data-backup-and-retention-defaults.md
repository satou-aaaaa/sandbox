# 0020. 顧客データ（data/clients.json等）のバックアップ・保持期間・暗号化前提

Status: Accepted
Date: 2026-09-30

## Context（背景）

顧客の氏名・住所・財務情報は、単一の平文JSON（`data/clients.json`・`data/drafts.json`。
ADR-0003でDB不採用は決定済み）にローカル保存される。一方で、そのファイルを
守る・失わないための仕組みが整理されていなかった（Issue #183）。

- **バックアップ手段が未整備**: 既存のバックアップ相当は「CSVエクスポート」
  のみで、許可種別ごとの `Detail` が失われ復元用としては不十分（#74）。
  ファイル破損・誤削除時の復旧手順も文書化されていなかった。
- **平文保存**: OSのディスク暗号化に依存している前提が、どこにも明記されていなかった。
- **保持期間・削除の方針なし**: 受任終了後の顧客データをいつ消すかの運用がなかった
  （個人情報保護法の「利用目的を達成したときは遅滞なく消去するよう努める」
  という努力義務〈同法22条〉の観点）。
- 下書き（`data/drafts.json`）が古いまま残り続ける可能性があった。

Issue #183の初回コメントで、実装前に発注者の判断が必要な論点（世代数・
実行タイミング、暗号化前提の明記可否、保持期間の具体日数、下書き警告の
閾値日数、実際の運用OS）を確認する必要があるとして一旦保留したが、
発注者から「実装方針はエージェントの推奨どおりで良い」と包括承認された
（同Issueのコメント参照）。本ADRは、その際に採用した推奨デフォルト値と
その根拠を記録する。

## Decision（決定）

次の4点を導入する。**いずれも推奨デフォルト値であり、実運用に応じて
発注者が調整できる**（値を変える場合、本ADRの内容が古くなるため、
必要なら新しいADRまたは本ADRの更新PRで値を追従させること）。

1. **世代バックアップ（`src/core/reminders/backup.js`）**:
   `withFileLock` で保護された書き込み処理の内部、新しい内容を書き出す
   直前に、書き換え前のファイル内容を `<対象ファイルと同じディレクトリ>/backup/`
   （既定: `data/backup/`）へ `<base>-<ISO8601タイムスタンプ>-<連番>.json`
   という名前でコピーし、**直近7世代**だけを残して古いものを自動削除する。
   対象は `data/clients.json`・`data/drafts.json` の両方。元ファイルが
   まだ存在しない（初回書き込み）場合は何もしない。
   - タイムスタンプの `:` は Windows のファイル名に使えないため `-` に
     置換する。同一ミリ秒内の連続書き込みでもファイル名の文字列比較が
     呼び出し順と一致するよう、ランダム値ではなくプロセス内の単調増加する
     連番をタイブレーカーに使う。
   - **クライアント本体データ（`clients.json`・`drafts.json`）を自動的に
     削除する機能は実装しない**。自動削除の対象は、あくまで `backup/`
     配下の複製（直近7世代を超えた分）のみ。本体データの削除は常に
     人手操作（既存の `client:remove` 等）。
   - `npm run data:backup`（一覧表示 / `-- --now` で手動バックアップ）・
     `npm run data:restore -- <clients|drafts> [世代番号]`
     （一覧表示 / 指定世代からの復元。復元前の内容も同じ仕組みで退避する）
     のCLIを用意する（`scripts/data-backup.js`・`scripts/data-restore.js`）。
2. **データ取り扱い方針の明記**: 本ツールは**OSのディスク暗号化
   （BitLocker・FileVault等）が有効であることを前提**とする。アプリ自体は
   暗号化・復号を行わない（`docs/DEVELOPMENT_GUIDE.md` 6章に明記）。
   保持期間は「**受任終了後1年を目安に削除を検討する**」という運用上の
   推奨にとどめる。個人情報保護法の解釈に関わる論点であり、具体的な
   年数・判断は発注者（行政書士本人）の業務上の責任で行うべき事柄のため、
   断定はせず「目安」という表現にする。削除手順そのものの自動化
   （自動削除バッチ等）は実装しない（上記1の「自動削除しない」方針と一貫）。
3. **下書きの有効期限警告**: `src/web/draftStore.js` に
   `DRAFT_STALE_THRESHOLD_DAYS`（既定30日）と `isDraftStale()` を追加し、
   下書き一覧画面（`src/web/draftsPage.js`）で、作成から30日を超えた
   下書きに「作成から30日以上経過」の警告を表示する。**自動削除はしない**
   （警告表示のみ。削除するかどうかは常に人手操作）。
4. **Windowsでのファイル権限確認手順**: `docs/DEVELOPMENT_GUIDE.md` に、
   `data/` 配下が自分のみアクセス可能であることを確認する簡易な運用メモを
   追記する（コード変更は行わない。アクセス制御自体はOS機能に委ねる）。

## Consequences（影響）

- ファイル破損・誤削除からの復旧手段ができ、CSVエクスポートに頼らず
  `Detail` を含む完全な状態へ復元できるようになる。
- `withFileLock` 内でのコピー（バックアップ）処理が増える分、書き込みの
  レイテンシがわずかに増える。ローカル・単一プロセス・小規模ファイル
  （顧客数十〜数百件程度を想定）という運用規模では実用上問題にならない
  と判断した。既存のカオステスト（同時書き込み競合の回帰テスト）に、
  世代バックアップを伴う同時書き込みのケースを追加し、破損・世代数超過が
  無いことを確認した。
- `backup/` 配下も実データを含むため、`data/` 全体が `.gitignore` 対象で
  あることに変わりはない（NFR-5）。バックアップ先を `data/` の外に
  置かない（外部送信はもちろん、意図せずコミット対象になることも避けるため）。
- 世代数（7）・保持期間の目安（1年）・下書き警告の閾値（30日）は、
  今回発注者の個別判断を仰がず「一般的に妥当と考えられる値」を
  エージェントが推奨として選び、包括承認のもとで採用した値である。
  実際の受任件数・運用頻度に応じて発注者が変更してよい
  （世代数は `backupBeforeWrite`/`restoreFromBackup` の `generations` 引数、
  閾値日数は `DRAFT_STALE_THRESHOLD_DAYS` を変更するだけで調整できる）。
- 見直しのトリガー: 顧客数が大きく増えバックアップのI/Oコストが無視できなく
  なった場合、または複数プロセス構成へ移行する場合（`fileLock.js` の
  スコープ外事項と同様、ADR-0003の見直しとあわせて再検討）。
